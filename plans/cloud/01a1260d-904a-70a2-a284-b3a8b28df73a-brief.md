### Design decisions already taken by the maintainer (2026-10-14)

Write these into `ROADMAP.md` as decisions; do not reopen them.

- **Format:** Atom (RFC 4287) by default; `format: rss` (RSS 2.0 only) or
  `format: both` in `config/feed.yaml`. Atom lands at `feed.xml`, RSS 2.0 at
  `rss.xml` (decided by the brief's author, a sensible default — record it).
- **Entries:** pages whose `meta.layout` is in the config key `layouts` (default
  `['pages/post.pug']`, the same rule and default as theme-blog's
  `blog.post_layouts`), plus optional `include` href patterns (`*` matches any
  run of characters including `/`, anchored — the same matcher as
  plugin-sitemap's `exclude`). A page is left out when its frontmatter says
  `feed: false`, when its effective robots (`meta.robots || app.robots`)
  contains `noindex`, when it has no `layout` or no string `href`, or when it has
  no usable date. Newest first, at most `limit` entries per feed (default 20).
- **Content:** the page's rendered HTML (`content` in pagesData — the Markdown
  body as HTML, without the layout) as Atom `<content type="html">`; for RSS
  2.0 decide between `<description>` (the spec's item body) and the common
  `content:encoded` extension (with `<description>` as the summary), and record
  it. In the content, root-relative and relative `href`/`src`/`srcset`/`poster` URLs are made
  absolute against origin + basePath + the page's href; `meta.description`
  (else `meta.lead`) as Atom `<summary>`. `content: summary` in config switches
  to summary only.
- **Paths, per language:** the default language (`app.lang`) at `/feed.xml`
  (and `/rss.xml`), every other language at `/<lang>/feed.xml`. A page's
  language is `meta.lang`, else `app.lang`. A monolingual site gets just
  `/feed.xml`. Never one merged multi-language feed. A language with no entries
  gets no feed file (decide whether it warns; record it).

### Nera facts the design rests on (verified 2026-10-11 against core 4.15.1 for plugin-sitemap; nothing relevant changed in 4.16.x)

- **Plugin contract.** A plugin is an ESM module exporting any of
  `getAppData({ app, pagesData })` → a new `app` (plain object),
  `getMetaData({ app, pagesData })` → a new pagesData array, and
  `getAssets({ app, pagesData })` → `[{ from, to }]`. A wrong return type is
  dropped by core with only a console warning, so return the right shape in every
  branch. Keep hooks synchronous. A site loads published plugins from its
  `package.json` dependencies whose names start with `@nera-static/plugin-`, and
  local ones from `folders.plugins` (e.g. `plugins/<name>/index.js`). Order:
  `config/plugin-order.yaml` `start:`, then alphabetical, then `end:`.
- **`getAssets` runs after every plugin's `getAppData`/`getMetaData`** with the
  final `app` and `pagesData`, so it sees content other plugins rewrote
  (plugin-images turns `<img>` into `<picture>` with `srcset`; plugin-code-blocks
  wraps code in markup) and pages they generate. Entry: `from` absolute,
  `to` relative to `public/` (no leading `/`, no `..`). Exists since core
  **4.13.0**; an older core never calls it, so guard the core version in
  `getAppData` exactly as plugin-sitemap's `src/guard.js` does, and declare
  `peerDependencies: { "@nera-static/core": ">=4.13.0" }`.
- **Never write into `public/` from a hook**: core deletes `public/` after the
  plugins ran. Write to `<site>/.nera-cache/feed/…` and return entries (sitemap's
  D1). Copy order is theme → plugins → site, so a site's own `assets/feed.xml`
  wins.
- **`meta.href`** is logical: `/<path>.html`, leading slash, never prefixed with
  `base_path`. `app.basePath` is `''` or `/foo` (normalised). Core rewrites
  `base_path` only in HTML/CSS/webmanifest/JSON — **not** in `.xml`, so the
  plugin applies `app.basePath` itself, and also inside entry content (core's
  rewrite of the page HTML happens later and never reaches the feed).
- **Origin:** `app.origin` (config/app.yaml), else `app_origin` in
  `config/canonical-links.yaml`, trailing slashes trimmed — same order as
  plugin-sitemap (`resolveOrigin` in its `src/config.js`). No origin → one
  warning naming both places, no feed (relative URLs are invalid in a feed).
  Reuse sitemap's URL joining and percent-encoding (`src/urls.js`, `encodePath`
  never double-encodes).
- **Dates.** Core parses frontmatter with `yaml` and the `timestamp` tag:
  unquoted `date: 2026-01-02` → a `Date` at UTC midnight; quoted → string.
  `meta.createdAt = frontmatter.createdAt || frontmatter.date || file birthtime`,
  and the plugin cannot tell the birthtime fallback from an authored value.
  **So the entry date comes from frontmatter `date` (then authored `published`
  if you choose to support it — record it), never from `createdAt` alone**;
  `updated` (theme-blog's key) else `lastmod`/`updatedAt` gives Atom
  `<updated>`, falling back to the published date. A post with no usable date is
  skipped with one warning listing the hrefs (decide; record). The feed-level
  `<updated>` is the newest entry's updated date — never "now", so builds stay
  byte-identical.
- **Atom requires** a stable `<id>` per feed and entry: use the absolute URL
  (tag URIs are an alternative — decide, record; the URL must not change when
  only the date does). Atom also requires an author at feed or entry level:
  `meta.author`, else config `author`, else `app.name`/the site title — decide
  the chain and record it.
- **Site title / language:** `app.name` is the site name in `config/app.yaml`
  (check what the `nera new` scaffold writes — fetch the CLI template, see
  below), `app.lang` the default language, `app.translations[lang][key]` the
  translations core's `t()` reads.
- **Templates.** Plugin views are published to a site with
  `npm run publish-template`, a `bin/publish-template.js` calling
  `publishTemplates({ pluginName, sourceDir, templateFiles, force })` from
  `@nera-static/plugin-utils` (it copies into `views/vendor/<plugin-name>/` and
  skips when that folder exists, unless `--force`). Model: plugin-tags'
  `bin/publish-template.js` and its `package.json` `bin` + `scripts` entries.
  Template markup and any BEM classes are a public contract (a change is major).
- **Config** is read from the **site**: `getConfig(path.resolve(cwd,
  'config/feed.yaml'))` (honour `app.folders.config` as sitemap does); it returns
  `{}` when the file is missing, so every key needs a JS fallback; read it inside
  the hook. The `config/feed.yaml` inside the package is documentation of the
  defaults and ships in `files`.
- **Pages without `layout` are never rendered** by core, so they never belong in
  a feed.
